# Сделает — Search & Ranking

Этот документ описывает целевую архитектуру поиска, квалификации, обогащения, проверки, ранжирования и формирования shortlist.

## 1. Основная цель

Поиск должен оптимизироваться не под максимальное число найденных исполнителей, а под вероятность получить несколько качественных, сопоставимых и объяснимо сильных вариантов.

Сервис обязан уменьшать объём выбора, а не переносить работу поисковика на пользователя.

## 2. Pipeline

Целевая последовательность:

`discover → deduplicate → qualify → enrich → verify → rank → shortlist → outreach → compare offers`

Каждый этап имеет отдельные лимиты и критерии качества.

## 3. Discovery

Задача этапа — собрать достаточно широкий сырой пул.

Источники могут включать:

- web search;
- официальный сайт;
- 2GIS;
- Яндекс Карты;
- Яндекс Исполнители;
- Avito;
- другие разрешённые публичные источники.

Discovery не равен shortlist.

Плохая практика: взять первые 5 результатов и считать поиск завершённым.

Хорошая практика: исследовать более широкий пул, затем квалифицировать и сократить.

## 4. Deduplication

Нужно объединять одного исполнителя, найденного в разных источниках.

Кандидаты для merge:

- одинаковый домен;
- одинаковый телефон;
- совпадающий официальный сайт;
- одинаковое/сильно похожее название + география;
- подтверждённые cross-source идентификаторы.

После merge источники и факты должны сохраняться, а provenance не теряться.

## 5. Qualification

Qualification отвечает на вопрос: «этот кандидат вообще подходит под задачу?»

Минимальные классы:

- `qualified`;
- `weak_match`;
- `excluded`;
- `needs_review`.

Причина квалификации должна быть объяснима.

Примеры критериев:

- выполняет нужный вид работ;
- работает в нужной географии;
- это реальная компания/мастер, а не информационная статья;
- профиль не является агрегатором/каталогом без собственного исполнения;
- нет очевидного несоответствия категории.

## 6. Enrichment

На этом этапе кандидат обогащается данными:

- официальный сайт;
- телефон;
- email;
- дополнительные контакты;
- адрес/география;
- факты по услуге;
- гарантия;
- цена/ориентир;
- сроки;
- материалы;
- профили на площадках;
- provenance каждого факта.

Enrichment должен выполняться после первичной квалификации, чтобы не тратить ресурсы на явно нерелевантных кандидатов.

## 7. Email enrichment

Для компаний с официальным сайтом crawler должен искать публичные контакты минимум на:

- целевой странице;
- главной странице;
- в перспективе — `Контакты`, `О компании`, `Реквизиты`, релевантных service pages.

Источники email:

- `mailto:`;
- JSON-LD;
- публичный текст страницы при безопасном извлечении.

Статусы:

- `found`;
- `no_website`;
- `not_crawled`;
- `not_found`.

Нужно хранить `emailSourceUrl`, когда возможно.

## 8. Verify

Проверка — отдельный слой от обнаружения факта.

Статусы:

- `confirmed`;
- `claimed`;
- `unknown`;
- `risk`.

Пример:

- гарантия на официальном сайте → `claimed` или `confirmed` в зависимости от модели верификации;
- телефон найден на официальном сайте → `confirmed` как опубликованный контакт;
- срок нигде не найден → `unknown`;
- негативный внешний сигнал → `risk` с обязательным источником.

## 9. Rank до получения предложений

До outreach score — технический инструмент сортировки, но пользователю показываются причины, а не абстрактные баллы.

Факторы ранжирования:

- соответствие категории;
- география;
- качество источника;
- официальный сайт/профиль;
- полнота контактов;
- подтверждённые профильные факты;
- качество provenance;
- отсутствие risk signals;
- разнообразие shortlist.

Нельзя давать слишком большой вес просто количеству источников.

## 10. Diversity

Shortlist не должен состоять из пяти почти одинаковых кандидатов, если существуют сильные альтернативы.

При категории, где уместны и компании, и частные мастера, shortlist может включать разные типы, если пользователь не задал жёсткое предпочтение.

Diversity не должна ухудшать качество: слабый кандидат не попадает в shortlist только ради разнообразия.

## 11. Shortlist

Основной shortlist:

- целевой размер: 3;
- допустимый максимум: 5;
- при недостатке качественных кандидатов лучше показать 2 сильных, чем 5 слабых.

Дополнительные уровни:

- `recommended` — основные 3;
- `alternatives` — ещё подходящие;
- `researched` — остальные проверенные.

Пользователь должен видеть общее число исследованных кандидатов, но не обязан просматривать их все.

## 12. Лимиты поиска

Не использовать одну константу `limit` как бизнес-логику всего pipeline.

Целевая конфигурация:

```text
discoveryLimit
qualificationLimit
enrichmentLimit
verificationLimit
outreachLimit
shortlistLimit
```

Тариф задаёт эти параметры, но pipeline остаётся одинаковым.

## 13. Тарифы — предварительная модель

### Basic

- глубина: до ~5 сильных кандидатов;
- shortlist: до 3–5;
- базовая проверка;
- единый запрос;
- базовое сравнение.

### Extended

- глубина: ~5–10;
- shortlist: 3–5;
- больше источников;
- более глубокое enrichment/verification;
- расширенные альтернативы и сравнение.

### Max

- глубина: ~10–20;
- shortlist: сначала 3 основных;
- полный исследованный пул доступен отдельно;
- глубокая проверка;
- расширенное сравнение предложений;
- больше возможностей выбора без перегрузки основного экрана.

Цифры являются продуктовой гипотезой и должны калиброваться по данным.

## 14. Outreach selection

Отправлять запрос нужно не всем обнаруженным кандидатам автоматически.

Нужны критерии допуска к outreach:

- кандидат квалифицирован;
- есть допустимый контакт/канал;
- контакт имеет provenance;
- нет блокирующего risk signal;
- пользователь явно подтвердил действие для автоматического канала.

`outreachLimit` может быть меньше `qualificationLimit`.

## 15. Compare offers

После получения ответов формируется новая модель сравнения.

Нужно извлекать и нормализовывать:

- total price;
- work price;
- materials included / excluded;
- список включённых работ;
- срок;
- гарантию;
- замер;
- доставку;
- демонтаж;
- дополнительные условия;
- неопределённости.

Если предложения несопоставимы, интерфейс обязан это показать.

Пример:

- `31 000 ₽` — материалы отдельно;
- `37 000 ₽` — всё включено;
- `48 000 ₽` — всё включено + дополнительные работы.

Нельзя автоматически объявлять первое предложение самым выгодным.

## 16. Ranking после ответов

После ответа кандидат может подняться или опуститься относительно первоначального ranking.

Факторы:

- полнота предложения;
- итоговая сопоставимая стоимость;
- состав работ;
- материалы;
- сроки;
- гарантия;
- количество неопределённостей;
- соответствие исходному ТЗ.

Система должна формулировать объяснение вроде:

- `Наиболее полное предложение`;
- `Дешевле, но материалы не включены`;
- `Дороже, зато включает дополнительные работы`;
- `Срок не указан — нужно уточнение`.

## 17. Quality gates

Переход кандидата между этапами должен иметь quality gate.

Примеры:

- discovery → qualification: есть идентифицируемый исполнитель;
- qualification → enrich: услуга и география достаточно релевантны;
- enrich → verify: есть данные, заслуживающие проверки;
- verify → shortlist: качество выше минимального порога;
- shortlist → outreach: допустимый контакт + пользовательское действие;
- outreach → compare: получен ответ с данными или отмечена неполнота.

## 18. Наблюдаемость

Для каждой search run желательно сохранять:

- сколько кандидатов найдено на каждом источнике;
- сколько осталось после dedup;
- сколько исключено qualification;
- сколько enrichment попыток выполнено;
- сколько сайтов успешно просканировано;
- сколько email/телефонов найдено;
- сколько кандидатов попало в shortlist;
- причины исключения/понижения;
- latency этапов;
- ошибки провайдеров.

Это позволит улучшать качество поиска на данных, а не на ощущениях.

## 19. Anti-patterns

Не делать:

- `первые 5 результатов = лучшие 5`;
- `чем больше карточек, тем лучше тариф`;
- ranking только по числу источников;
- скрывать причины отсутствия email;
- смешивать claimed и confirmed;
- сравнивать только цену без состава;
- отправлять запрос всем найденным кандидатам без подтверждения;
- добавлять новую категорию без category spec.
