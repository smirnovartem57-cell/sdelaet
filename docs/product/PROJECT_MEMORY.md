# Сделает — Project Memory

Статус: source of truth для принятых продуктовых решений.

Этот файл хранит устойчивую продуктовую логику проекта «Сделает». Детали реализации, временные эксперименты и category-specific правила должны жить в профильных документах, а не раздувать этот файл.

## 1. Что такое «Сделает»

«Сделает» — сервис, который помогает пользователю не искать исполнителя вручную по множеству сайтов и площадок, а пройти путь:

`описал задачу → сервис разобрался → нашёл источники → проверил кандидатов → сформировал единый запрос → собрал сопоставимые предложения → объяснил различия → помог выбрать`

Сервис не должен превращаться в каталог ссылок или ещё один marketplace. Его ценность — исследование, нормализация, проверка и объяснимый shortlist.

## 2. Основная пользовательская ценность

Пользователь не должен:

- самостоятельно обходить 5–20 сайтов;
- разбираться во всех технических тонкостях услуги до начала поиска;
- вручную сравнивать несопоставимые предложения;
- самостоятельно проверять источники и контакты кандидатов;
- теряться в большом списке исполнителей без объяснения, кого выбирать и почему.

Результат сервиса — не «мы нашли 20 вариантов», а «мы исследовали рынок и сузили выбор до нескольких вариантов, между которыми действительно имеет смысл выбирать».

## 3. Основной search pipeline

Целевая архитектура поиска:

`discover → deduplicate → qualify → enrich → verify → rank → shortlist → outreach → compare offers`

Этапы должны быть логически разделены. Нельзя использовать один технический лимит для всех этапов.

Минимальный набор независимых лимитов:

- `discoveryLimit` — сколько сырых кандидатов исследуем;
- `qualificationLimit` — сколько кандидатов квалифицируем глубже;
- `enrichmentLimit` — сколько кандидатов обогащаем контактами и фактами;
- `outreachLimit` — скольким кандидатам можно подготовить/отправить запрос;
- `shortlistLimit` — сколько кандидатов показываем в основном shortlist.

## 4. Количество найденных ≠ количество показанных

Более высокий тариф должен увеличивать глубину исследования и качество отбора, а не количество карточек перед глазами пользователя.

Правило продукта:

- основной shortlist — максимум 3–5 кандидатов;
- при большем тарифе можно исследовать 10–20 и более кандидатов;
- дополнительные релевантные варианты показываются вторым уровнем;
- весь исследованный пул должен быть доступен по раскрытию, но не перегружать основной экран.

Целевая структура выдачи при глубоком поиске:

1. `Рекомендуем рассмотреть` — 3 основных варианта;
2. `Ещё подходят` — дополнительные сильные кандидаты;
3. `Остальные проверенные` — полный исследованный пул.

## 5. Тарифная логика поиска

Тарифы не должны быть реализованы как три разные поисковые системы.

Предварительная модель:

- базовый: до ~5 глубоко обработанных кандидатов;
- расширенный: ~5–10;
- максимальный: ~10–20;
- при любом тарифе основной shortlist ограничен 3–5 кандидатами.

Точные цифры могут меняться после тестов. Не фиксировать бизнес-логику на технической константе вроде `maxSites=5`.

## 6. Ранжирование до и после ответа

### До получения предложения

Ранжирование строится по соответствию задаче и проверенным сведениям:

- релевантность нужной услуге;
- география;
- подтверждённый официальный сайт/профиль;
- наличие контактов;
- подтверждённые профильные факты;
- качество и происхождение источников;
- отсутствие явных risk signals.

### После получения предложения

Приоритет меняется. Главным становится реальное предложение по одинаковому ТЗ:

- итоговая стоимость;
- что входит в стоимость;
- материалы;
- срок;
- гарантия;
- дополнительные работы/условия;
- полнота ответа;
- сопоставимость предложения с другими.

Нельзя сравнивать только голые цены, если состав предложений отличается.

## 7. Объяснимость вместо абстрактного рейтинга

Не использовать выдуманные `Trust Score`, проценты надёжности или псевдоточные оценки без доказательной базы.

Основные статусы фактов:

- `confirmed` — подтверждено источником;
- `claimed` — заявлено кандидатом/источником, но не подтверждено независимо;
- `unknown` — не удалось установить;
- `risk` — найден конкретный сигнал риска.

Пользователь должен понимать, почему кандидат выше или ниже другого.

Пример:

- выполняет нужный тип работ;
- работает в нужном городе;
- найден официальный сайт;
- опубликованы телефон и email;
- подтверждена гарантия;
- срок не удалось подтвердить.

## 8. Provenance — происхождение данных

Любой важный факт желательно хранить вместе с источником.

Особенно:

- email;
- телефон;
- официальный сайт;
- цена;
- гарантия;
- сроки;
- отзывы/репутационные сигналы;
- негативная информация.

Негативная информация всегда показывается как сигнал из конкретного внешнего источника, а не как утверждение сервиса.

## 9. Контакты и email

Для email важно различать причину отсутствия:

- `found` — публичный email найден;
- `no_website` — официальный сайт не определён;
- `not_crawled` — сайт не был глубоко проверен;
- `not_found` — сайт проверен, публичный email не найден.

Желательно хранить:

- `email`;
- `emails[]`;
- `emailStatus`;
- `emailSourceUrl`;
- тип источника (`official_site`, официальный профиль и т. п.).

Для автоматической отправки приоритет — публичный контактный email самого исполнителя, происхождение которого можно показать пользователю.

## 10. Outreach и безопасность отправки

Автоматическая отправка по email — отдельный явно обозначенный канал.

UX-принцип:

`выбрать почту → проверить письмо → явное подтверждение → отправить`

Один клик по «Почта» не должен отправлять письмо.

Сейчас действует SAFE MODE:

- frontend не выполняет реальную отправку из request flow;
- backend имеет allowlist тестовых адресов;
- случайная отправка реальным кандидатам блокируется.

Перед production-отправкой обязательны:

- явное подтверждение пользователя;
- rate limiting;
- защита от повторной отправки;
- прозрачный recipient и текст письма;
- журналирование статусов.

## 11. Реальные статусы outreach

Статусы не декоративные:

- `prepared` — запрос подготовлен;
- `sent` — отправка принята локальной почтовой системой;
- `delivered` — внешний SMTP-сервер принял письмо (`250 OK`);
- `replied` — реальный входящий ответ сопоставлен с запросом;
- `failed` — зафиксирована ошибка.

Ответы должны привязываться к конкретному `requestId` и отображаться в контексте кандидата.

## 12. Ручные каналы

Avito, Яндекс Исполнители, телефон и другие каналы без безопасной автоматизации должны иметь отдельный manual-flow:

`подготовить запрос → скопировать → открыть площадку/контакт → пользователь отправляет вручную`

Автоматические и ручные действия должны быть визуально разделены.

## 13. Карточка кандидата

Карточка должна быстро отвечать на вопросы:

1. Кто это?
2. Почему подходит?
3. Что подтверждено?
4. Что неизвестно?
5. Какие есть контакты?
6. Какие источники использованы?
7. Как связаться?
8. Получен ли ответ и что предложено?

Приоритет — объяснимость и снижение когнитивной нагрузки.

## 14. Category-driven продукт

Категории не должны быть просто строками в dropdown.

Новая категория считается готовой только после заполнения обязательной спецификации из `categories/CATEGORY_TEMPLATE.md`.

Каждая категория должна определить минимум:

- intake;
- discovery;
- qualification;
- verification;
- единый запрос;
- нормализацию предложений;
- ranking до ответа;
- ranking после ответа;
- risk signals;
- источники и контакты.

## 15. Текущая эталонная категория

Первая рабочая категория:

`balcony-insulation` — утепление / отделка балкона и лоджии.

Она должна быть эталоном для подключения следующих категорий.

См. `categories/balcony-insulation.md`.

## 16. Принцип обновления памяти

В этот файл добавляются только принятые устойчивые решения.

Если решение относится только к:

- алгоритму поиска — `SEARCH_AND_RANKING.md`;
- конкретной категории — соответствующий файл в `categories/`;
- временной технической реализации — код/issue/ADR, но не Project Memory.
