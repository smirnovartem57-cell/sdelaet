# Категория: утепление балкона / лоджии

```yaml
categoryId: balcony-insulation
serviceCode: BALCONY_INSULATION
domain: CONSTRUCTION
category: HOME_REPAIR
subcategory: WINDOWS_BALCONIES
name: Утепление балкона / лоджии
shortName: Утепление балкона
status: READY
expertProfileVersion: 1.1
seasonality: autumn_winter_high
launchPriority: P1
```

Этот файл — эталонная Expert Service Specification для первой категории «Сделает». Его задача — позволить сервису знать значительно больше, чем он спрашивает у клиента, и получать от исполнителей короткие, но сопоставимые предложения.

## 1. Цель категории

Пользователь хочет получить более тёплый и пригодный для нужного сценария балкон/лоджию, не разбираясь самостоятельно в технологии утепления, остеклении, пароизоляции, примыканиях и составе сметы.

Сервис должен:

1. понять желаемый результат;
2. определить, достаточно ли исходных данных для предварительного расчёта;
3. выявить критические ограничения;
4. сформировать единое короткое ТЗ нескольким исполнителям;
5. привести ответы к сопоставимому виду;
6. показать, что включено, что отсутствует и где возможны доплаты/риски.

## 2. Что входит в сценарий

Основной сценарий:

- утепление стен, пола, потолка и/или парапета;
- устройство тёплого контура;
- герметизация и работа с примыканиями;
- пароизоляционный/влагозащитный слой, когда он требуется выбранной системой;
- черновая и чистовая отделка, если она входит в задачу;
- демонтаж старой отделки/неудачного утепления;
- электрика, освещение и электрический тёплый пол как опции;
- откосы, подоконники, пороги и вывоз мусора как сопутствующие позиции.

Смежные сценарии не смешивать автоматически:

- новое остекление или полная замена окон;
- конструктивное усиление балконной плиты/парапета;
- изменение фасада;
- объединение лоджии/балкона с комнатой;
- перенос центрального отопления;
- изготовление мебели;
- ремонт протечек фасада/кровли, если это самостоятельная причина дефекта.

## 3. Типовые Jobs to be Done

- «Хочу сделать кабинет и пользоваться зимой».
- «Хочу, чтобы на лоджии было заметно теплее».
- «Нужно утеплить и отделать под ключ».
- «Промерзает/дует, нужно понять причину и исправить».
- «Старое утепление сделано плохо — переделать».
- «Нужно утеплить только пол/потолок/стену».

## 4. Главный принцип Client Intake

Клиент не должен проектировать систему утепления. Мы не спрашиваем у него марку утеплителя, толщину плит, тип пароизоляции, способ крепления, монтажную пену, мембраны и другие профессиональные параметры, если он сам их не указал.

По умолчанию Client Intake — максимум 5 основных действий. Дополнительный вопрос задаётся только если ответ реально меняет состав работ, возможность получить сопоставимую цену или безопасность решения.

## 5. Client Intake — минимальный сценарий

### Шаг 1. Для чего нужен балкон/лоджия?

```yaml
field: goal
required: true
values:
  - winter_workspace        # кабинет / работа зимой
  - year_round_use          # круглогодичное использование
  - make_warmer             # просто сделать теплее
  - finish_and_insulate     # утеплить и отделать под ключ
  - fix_existing_problem    # промерзание / конденсат / сквозняк / переделка
  - other
```

Человеческие варианты интерфейса:

- Кабинет / рабочее место зимой
- Использовать круглый год
- Просто сделать теплее
- Утеплить и отделать под ключ
- Исправить промерзание / сырость / сквозняк
- Другое

### Шаг 2. Остекление уже есть?

```yaml
field: glazingStatus
required: true
values:
  - exists_seems_warm
  - exists_unknown
  - cold_or_single_glazing
  - no_glazing
  - needs_replacement
```

В интерфейсе не требуем от клиента знания камерности профиля. Допустимый ответ: «Есть, но не знаю какое».

### Шаг 3. Примерный размер

Достаточно одного из вариантов:

- длина × ширина;
- площадь пола;
- план/замеры на фото;
- «не знаю» + фотографии.

Высоту спрашивать только если без неё невозможно получить адекватный расчёт для конкретного исполнителя. Точные монтажные размеры относятся к `INSTALLATION_REQUIRED`.

### Шаг 4. Что нужно на выходе?

```yaml
field: finishScope
required: true
values:
  - insulation_only
  - insulation_and_finish
  - turnkey_with_electric
  - contractor_to_propose
```

Если выбран `turnkey_with_electric`, уточнить одной компактной группой: свет / розетки / электрический тёплый пол.

### Шаг 5. Фото

Рекомендуемый минимум — 3–5 фото:

1. общий вид от двери;
2. остекление и зона под ним/парапет;
3. пол + нижние примыкания;
4. потолок + верхние примыкания;
5. проблемная зона крупно, если есть сырость, плесень, промерзание или повреждения.

Фото не являются обязательными для создания заявки, но без них точность предварительного сравнения ниже.

## 6. Дополнительные вопросы — только по триггеру

Сервис может задать максимум 1–3 дополнительных вопроса после анализа исходных данных.

| Триггер | Вопрос | Почему нужен |
|---|---|---|
| `goal = winter_workspace/year_round_use` и остекление неизвестно | «Готовы рассмотреть замену/доработку остекления, если текущее не подходит для тёплого помещения?» | Без пригодного остекления утепление непрозрачных поверхностей может не дать нужного результата |
| Есть сырость/конденсат/плесень | «Проблема появляется зимой, после дождя или постоянно?» | Разделить теплотехническую проблему и возможное внешнее поступление воды |
| Нужен только отдельный участок | «Что именно утепляем: пол / потолок / стену / парапет?» | Определяет объём работ |
| Старая отделка/утепление | «Переделываем существующее или можно демонтировать полностью?» | Влияет на демонтаж и скрытые дефекты |
| Пользователь хочет объединить с комнатой | Не продолжать как обычное утепление; вывести предупреждение и перевести в сценарий, требующий проверки перепланировки | Юридические и конструктивные ограничения |

## 7. Что определяем автоматически

По описанию и фото сервис пытается определить и хранит вместе со статусом достоверности:

- балкон или лоджия — `observed/inferred`;
- наличие остекления — `observed`;
- ориентировочный тип остекления — только `observed/inferred`, если это действительно различимо;
- наличие старой отделки/утепления — `observed`;
- материал видимого парапета/стен — `observed/inferred`;
- видимые щели, повреждения, следы влаги/плесени — `observed`;
- ориентировочный объём демонтажа — `inferred`;
- наличие электрических точек/освещения — `observed`;
- примерную геометрию — `observed/inferred`;
- потенциально проблемные примыкания — `inferred`.

Нельзя по обычной фотографии надёжно утверждать:

- фактическое сопротивление теплопередаче;
- точный состав стены/пирога;
- точную толщину существующего утеплителя;
- герметичность скрытых швов;
- прочность плиты/парапета;
- отсутствие скрытого увлажнения;
- соответствие остекления требуемому тепловому режиму.

Такие данные получают статус `unknown` или `requires_site_inspection`.

## 8. Внутренняя техническая модель

### 8.1. Сначала проверяем достижимость цели

Утепление стен, пола и потолка нельзя оценивать отдельно от остекления и примыканий, если пользователь хочет круглогодичное тёплое помещение.

Для целей `winter_workspace` и `year_round_use` эксперт обязательно проверяет:

- пригодность существующего остекления;
- состояние монтажных швов/примыканий;
- холодные участки по периметру;
- парапет и боковые ограждения;
- пол и потолок;
- необходимость источника тепла, допустимого для данного объекта;
- риск конденсации при изменении температурно-влажностного режима.

### 8.2. Тёплый контур

Система должна рассматривать помещение как единый контур. Красный флаг — предложение утеплить только видимые стены при заявленной цели «кабинет зимой», не оценив остекление, пол, потолок и основные примыкания.

### 8.3. Воздухопроницаемость и примыкания

Даже достаточный слой теплоизоляции не компенсирует выраженные продувания. Внутренняя модель должна отдельно учитывать:

- примыкание оконного блока;
- углы;
- стык парапета и пола;
- стык потолка/верхней плиты;
- проходы коммуникаций;
- открытые/разрушенные монтажные швы.

Для оконных монтажных узлов нормативным ориентиром служит ГОСТ 30971-2012; при production-проверке всегда использовать актуальную редакцию.

### 8.4. Влага, пар и конденсат

Сервис не назначает конкретный «пирог» без исходных данных. Но обязан проверить, предусмотрена ли исполнителем логика управления влагой для выбранной конструкции.

Красные флаги:

- обещание «конденсата точно не будет» без обследования и расчёта;
- утепление по явно влажному основанию без выяснения причины;
- игнорирование наружной протечки/разгерметизации;
- описание системы только словами «пена + утеплитель + отделка» без понимания примыканий и влагонакопления.

СП 50.13330.2024 используется как общий нормативный ориентир по тепловой защите и воздухопроницаемости ограждающих конструкций. Сервис не подменяет теплотехнический расчёт, когда он необходим.

### 8.5. Материалы

На этапе первичного подбора клиент не выбирает материал сам. Исполнитель должен указать предложенную систему и ключевые материалы.

Сервис сравнивает не бренд материала как таковой, а:

- где он применяется;
- толщину/слой, если заявлен;
- непрерывность решения;
- совместимость слоёв;
- наличие обработки примыканий;
- состав последующей отделки;
- что входит в цену.

Нельзя автоматически объявлять один утеплитель «лучше» другого без привязки к конструкции и цели.

### 8.6. Пол

Проверяем, включает ли предложение:

- подготовку основания;
- теплоизоляцию;
- основание под чистовое покрытие;
- само покрытие, если требуется;
- электрический тёплый пол отдельной строкой, если он нужен;
- поднятие уровня пола/порог как возможный эффект.

### 8.7. Электрика и отопление

Электрика должна идти отдельным понятным блоком: свет, количество розеток, тёплый пол, новые линии/автоматика — если они входят в расчёт.

Перенос радиатора, подключённого к общедомовой системе центрального отопления, на балкон/лоджию нельзя автоматически включать как допустимое решение. Для таких запросов требуется проверка действующих региональных правил переустройства/перепланировки. Для Москвы действующие требования прямо содержат соответствующие ограничения; в других регионах проверяется местное регулирование.

## 9. QUOTE_REQUIRED vs INSTALLATION_REQUIRED

### QUOTE_REQUIRED

Достаточно для предварительного сопоставимого предложения:

- город/район;
- цель использования;
- наличие/состояние остекления на уровне, доступном клиенту;
- примерный размер;
- утепление только или с отделкой;
- основные дополнительные опции;
- фото, если доступны;
- известные проблемы: сырость, промерзание, сквозняки, старое утепление.

### INSTALLATION_REQUIRED

Не заставляем клиента собирать до первичного расчёта:

- точные размеры каждой поверхности;
- точный состав основания;
- влажность конструкций;
- состояние скрытых монтажных швов;
- расчёт точки росы/влагонакопления;
- несущую способность конструкций;
- точные трассы электрики;
- детальную спецификацию крепежа и слоёв.

Эти параметры уточняются на замере/обследовании и получают `requires_site_inspection`, если они критичны.

## 10. Факторы стоимости

На цену чаще всего влияют:

- площадь и геометрия;
- балкон или лоджия;
- состояние и пригодность остекления;
- объём утепляемого контура;
- демонтаж старой отделки/утепления;
- состояние парапета и примыканий;
- выбранная система утепления и отделки;
- черновой пол и чистовое покрытие;
- электрика;
- электрический тёплый пол;
- сложность доступа/подъёма материалов;
- вывоз мусора;
- необходимость дополнительных ремонтных работ после вскрытия.

## 11. Типовые скрытые доплаты

Сервис отдельно проверяет наличие в цене:

- демонтажа;
- вывоза мусора;
- доставки/подъёма;
- материалов и расходников;
- подготовки основания;
- герметизации примыканий;
- работы с парапетом;
- чернового пола;
- чистового покрытия;
- потолка;
- откосов/подоконников/порогов;
- электрики;
- тёплого пола;
- замера;
- исправления дефектов, обнаруженных после демонтажа.

Если позиция нужна по ТЗ, но в ответе не указана, она не считается включённой автоматически.

1. итоговую ориентировочную стоимость;

## 14. Нормализация предложений

Главный показатель — `comparableTotalPrice`: максимально близкая к исходному ТЗ стоимость при одинаковом составе работ.

Правила:

1. `от X ₽` не считать расчётом по задаче;
2. материалы отдельно — не считать предложение автоматически дешевле варианта с материалами;
3. отсутствующую обязательную позицию помечать `missing`, а не считать включённой;
4. если точную стоимость можно дать только после замера, хранить предварительный диапазон/оценку отдельно;
5. дополнительные работы, предложенные исполнителем, отделять от базового ТЗ;
6. сравнивать одинаковый объём и явно показывать разницу комплектаций.

## 15. Когда предложения нельзя сравнивать напрямую

- одно включает отделку, другое только утепление;
- в одном включены материалы, во втором нет;
- одно требует замену остекления, второе считает существующее пригодным без пояснения;
- различается объём: полный контур против одной поверхности;
- неясно, включены ли демонтаж/пол/потолок/парапет;
- цена одного является рекламной «от», другого — расчётом по ТЗ;
- один исполнитель добавил обязательные подготовительные работы, второй их не оценил.

Статус: `NOT_DIRECTLY_COMPARABLE`, пока различия не нормализованы.

## 16. Красные флаги технического предложения

- «будет тепло зимой» без оценки остекления при явно холодном остеклении;
- цена без состава работ;
- отсутствие информации о материалах при заявлении «под ключ»;
- обещание полного отсутствия конденсата без проверки исходных условий;
- утепление по мокрому/повреждённому основанию без выяснения причины;
- игнорирование примыканий и явных продуваний;
- предложение перенести центральный радиатор без проверки допустимости;
- существенное изменение конструкций/парапета без указания необходимости обследования/согласования;
- «всё включено», но не раскрыты демонтаж, материалы, отделка и дополнительные расходы.

Красный флаг не означает автоматически, что исполнитель плохой; это повод запросить уточнение или снизить уверенность сравнения.

## 17. Проверка исполнителя

Must-have для сильной квалификации:

- явная услуга утепления/отделки балконов или лоджий;
- подтверждённая работа в нужной географии;
- профильные работы/портфолио либо профильная страница услуги.

Положительные сигналы:

- реальные примеры аналогичных объектов;
- описан состав работ;
- понятны материалы/система;
- гарантия сформулирована конкретно;
- официальный сайт/публичные контакты;
- прозрачные условия замера;
- предложение содержит исключения и возможные доплаты, а не скрывает их.

Reputation layer работает по общим правилам `TRUST_AND_REPUTATION.md`: сведения из внешних источников показываются как сигнал со ссылкой на источник, а не как бездоказательное утверждение «Сделает».

## 18. Статусы достоверности

Использовать единообразно:

- `confirmed` — подтверждено клиентом, документом или надёжным источником;
- `observed` — непосредственно видно в предоставленных данных/фото;
- `inferred` — предположение системы;
- `unknown` — данных недостаточно;
- `requires_site_inspection` — корректно определяется только на объекте.

Для данных об исполнителе дополнительно допустим `claimed` — заявлено самим исполнителем/на его сайте, но независимо не проверено.

## 19. Expert QA

Результат нельзя выпускать как уверенное сравнение без проверки:

### Technical completeness

- цель клиента понятна;
- остекление не проигнорировано;
- объём утепления определён;
- отделка и опции отделены;
- видимые проблемы учтены;
- `requires_site_inspection` не выданы за факты.

### Offer completeness

- цена имеет понятный тип;
- понятно, включены ли материалы;
- известен основной состав работ;
- отсутствующие позиции отмечены;
- доплаты вынесены отдельно;
- срок/замер/гарантия не выдуманы.

### Comparison integrity

- сравнивается одинаковый объём;
- рекламная цена «от» не победила расчёт по ТЗ;
- более дешёвая неполная смета не названа автоматически более выгодной;
- дополнительные работы не смешаны с базовой стоимостью;
- рекомендации объяснимы конкретными отличиями.

QA statuses:

- `PASS`
- `PASS_WITH_WARNINGS`
- `NEEDS_DATA`
- `EXPERT_REVIEW_REQUIRED`
- `FAIL`

## 20. Правило итоговой рекомендации

«Выгоднее» = не минимальная цифра, а лучшая сопоставимая стоимость при требуемом составе работ и приемлемом уровне неопределённости.

Допустимые формулировки:

- «Самое полное предложение по вашему ТЗ»;
- «Ниже по цене, но материалы оплачиваются отдельно»;
- «Дороже на X ₽, зато включены демонтаж и чистовая отделка»;
- «Сейчас напрямую сравнить нельзя: не указана стоимость материалов»;
- «Перед выбором нужен замер: исполнители по-разному оценили пригодность остекления».

Не использовать без доказательств:

- «самый надёжный»;
- «лучший мастер»;
- «точно не будет конденсата»;
- «так делать нельзя» без применимой нормы/контекста;
- «всё включено», если состав не раскрыт.

## 21. Discovery strategy

Запросы:

- `утепление балкона {city}`;
- `утепление лоджии {city}`;
- `тёплый балкон под ключ {city}`;
- `отделка и утепление лоджии {city}`.

Приоритет источников:

1. официальный сайт;
2. карты/каталоги как discovery;
3. профильные площадки частных мастеров;
4. web search для дополнительных фактов и официального сайта.

Исключать/понижать:

- DIY-статьи;
- магазины материалов без монтажа;
- оконные компании без реальной услуги утепления;
- агрегаторы без признака собственного исполнения;
- нерелевантную географию;
- общестроительные компании без профильных кейсов — `needs_review`.

## 24. Нормативные и справочные ориентиры

Перед использованием в production актуальность редакций должна проверяться автоматически/регламентно.

- СП 50.13330.2024 «Тепловая защита зданий» — теплотехническая логика и воздухопроницаемость ограждающих конструкций: https://docs.cntd.ru/document/1306326592
- ГОСТ 30971-2012 «Швы монтажные узлов примыкания оконных блоков к стеновым проемам» — монтажные швы и примыкания: https://docs.cntd.ru/document/1200102010
- Правовые ограничения перепланировки/переноса отопления должны проверяться по региону. Справочная подборка КонсультантПлюс: https://www.consultant.ru/law/podborki/perenos_radiatorov_otopleniya/

Нормативный источник является ориентиром для Expert QA, а не поводом генерировать пользователю длинную нормативную справку.
