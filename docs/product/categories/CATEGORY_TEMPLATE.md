# Сделает — Category Template

Этот файл определяет минимальный обязательный объём спецификации для новой категории.

Новая категория **не считается подключённой**, пока все обязательные разделы не заполнены и не проверены на реальных сценариях.

---

# 1. Identity

Обязательно указать:

```yaml
categoryId:
name:
shortName:
synonyms: []
seasonality:
status: draft|pilot|production
```

Нужно описать:

- что входит в категорию;
- что не входит;
- какие соседние категории легко спутать с ней;
- какие пользовательские формулировки должны маппиться сюда.

# 2. User intent / Jobs to be Done

Опишите типовые причины обращения пользователя.

Минимум:

- основной job;
- 3–7 частых вариантов задачи;
- что пользователь обычно не знает и ожидает, что сервис уточнит сам;
- что является конечным результатом услуги.

# 3. Intake — что спросить у пользователя

Определите обязательные и условные вопросы.

Для каждого поля:

```yaml
field:
label:
type:
required:
condition:
why_needed:
example:
```

Минимум нужно определить:

- географию;
- объём/размер задачи;
- текущее состояние;
- желаемый результат;
- критичные ограничения;
- сроки, если они важны;
- бюджет, если он действительно помогает подбору;
- фото/файлы, если они существенно повышают качество ТЗ.

# 4. Task normalization

Опишите, как свободное описание пользователя превращается в нормализованную задачу.

Нужно определить:

- canonical fields;
- единицы измерения;
- нормализацию терминов;
- вычисляемые параметры;
- допустимые неизвестные значения.

# 5. Discovery

Опишите стратегию обнаружения исполнителей.

Обязательно:

```yaml
search_queries:
  company: []
  private: []
  informational_exclusions: []
geo_strategy:
sources:
```

Для каждого источника:

- зачем он нужен;
- какие типы кандидатов оттуда ожидаем;
- какие поля обычно доступны;
- ограничения качества;
- нужно ли дополнительное подтверждение официального сайта/профиля.

# 6. Candidate types

Определите допустимые типы исполнителей:

- компания;
- частный мастер;
- бригада;
- специализированный подрядчик;
- другие типы, если нужны.

Укажите, допустимо ли смешивать их в одном shortlist и при каких условиях.

# 7. Deduplication rules

Опишите признаки одного и того же исполнителя:

- домен;
- телефон;
- email;
- название;
- адрес;
- профиль площадки;
- дополнительные category-specific признаки.

# 8. Qualification

Определите критерии релевантности.

Разделить на:

## Must-have

Без этого кандидат не считается подходящим.

## Strong positive signals

Факторы, повышающие приоритет.

## Weak / ambiguous signals

Недостаточные для уверенной квалификации.

## Exclusion rules

Причины исключения.

Примеры:

- информационная статья вместо исполнителя;
- магазин без услуг монтажа;
- неподходящая география;
- специализация на другой услуге;
- агрегатор без собственного исполнения.

# 9. Enrichment

Определите данные, которые желательно найти до shortlist.

Минимум:

- официальный сайт/профиль;
- телефон;
- email;
- география;
- профиль услуги;
- цена/ориентир, если опубликован;
- гарантия;
- сроки;
- материалы/бренды, если значимо;
- реквизиты/юридическая информация, если значимо.

Для каждого поля определить provenance.

# 10. Verification

Для каждого важного факта указать:

```yaml
fact:
source_priority:
confirmed_when:
claimed_when:
risk_when:
unknown_when:
```

Используем статусы:

- `confirmed`;
- `claimed`;
- `unknown`;
- `risk`.

# 11. Reputation / risk signals

Опишите, какие внешние проверки полезны именно для этой категории.

Для каждого сигнала:

- источник;
- что именно считаем сигналом;
- насколько он критичен;
- блокирует ли shortlist/outreach;
- как формулируем пользователю без недоказанных утверждений.

# 12. Email/contact policy

Определите:

- где допустимо брать email;
- какие email считаются публичными контактными;
- какие generic email допустимы (`info@`, `sales@`, `zakaz@` и т. п.);
- какие контакты не использовать;
- где искать телефон;
- какие manual channels поддерживаются.

Email status:

- `found`;
- `no_website`;
- `not_crawled`;
- `not_found`.

# 13. Uniform offer request

Нужно сформировать **единый запрос**, отправляемый всем кандидатам.

Обязательные части:

- краткое описание задачи;
- нормализованные параметры;
- что нужно рассчитать;
- какие вопросы обязательны;
- что считать полной ценой;
- какие условия нужно указать отдельно.

Формат должен позволять сравнивать ответы кандидатов между собой.

# 14. Required offer fields

Определите минимальный набор полей предложения:

```yaml
total_price:
work_price:
materials_price:
materials_included:
scope_included:
lead_time:
warranty:
measurement:
extra_costs:
notes:
```

Добавьте category-specific поля.

# 15. Offer normalization

Опишите правила приведения предложений к сопоставимому виду.

Нужно определить:

- что означает `итоговая стоимость`;
- как учитывать материалы;
- что делать с диапазоном цены;
- как учитывать цену `от`;
- какие позиции считаются дополнительными;
- как обрабатывать отсутствие данных;
- когда два предложения нельзя честно сравнить по цене.

# 16. Ranking before outreach

Опишите факторы ranking до получения коммерческого предложения.

Не показывать пользователю псевдоточные баллы без объяснения.

Для каждого фактора желательно задать:

- importance;
- positive signal;
- negative signal;
- explanation text.

# 17. Ranking after response

Определите, как меняется ranking после реальных предложений.

Минимум учитывать:

- сопоставимую итоговую цену;
- полноту состава;
- сроки;
- гарантию;
- количество неизвестных условий;
- соответствие исходному ТЗ.

# 18. Shortlist policy

Определите:

- целевой размер основного shortlist;
- допустимый максимум;
- требования к quality gate;
- правила diversity;
- когда лучше показать меньше кандидатов.

Базовое правило проекта: основной shortlist — 3–5 кандидатов максимум.

# 19. Card output

Опишите, что пользователь должен увидеть в карточке.

Минимум:

- тип кандидата;
- имя;
- география;
- почему подходит;
- подтверждённые факты;
- неизвестные сведения;
- risk signals;
- контакты;
- источники;
- published price с оговоркой, если есть;
- доступные каналы связи;
- статус outreach/ответа.

# 20. Comparison output

Опишите итоговый экран сравнения.

Нужно определить:

- главные колонки/показатели;
- как выделяем сильные стороны;
- как показываем неполноту;
- какие выводы система может формулировать;
- какие выводы нельзя делать без достаточных данных.

# 21. Test scenarios

Перед production категория должна иметь минимум:

- 5 типовых пользовательских задач;
- 2 пограничных сценария;
- 2 нерелевантных сценария;
- кейс без email;
- кейс без официального сайта;
- кейс с несколькими дублями;
- кейс с несопоставимыми ценами;
- кейс с неполным ответом исполнителя.

# 22. Acceptance checklist

Категория может перейти в production, если:

- [ ] intake заполнен;
- [ ] discovery queries проверены;
- [ ] exclusion rules определены;
- [ ] qualification работает на тестовом наборе;
- [ ] enrichment определён;
- [ ] provenance сохраняется;
- [ ] email/contact policy определена;
- [ ] verification rules определены;
- [ ] uniform request готов;
- [ ] offer schema определена;
- [ ] normalization определена;
- [ ] ranking before/after response определён;
- [ ] shortlist policy определена;
- [ ] карточка и comparison output определены;
- [ ] test scenarios пройдены;
- [ ] ручные и автоматические outreach-каналы безопасны.
