# Стандарт добавления продуктовых категорий

Обязательный стандарт для добавления каждой новой категории услуг в «Сделает».

## Главное правило

Новая категория не добавляется в продукт только на основании универсального промпта для ИИ или общего списка вопросов.

Сначала категория изучается отдельно, затем создаётся спецификация категории, и только после этого реализуются интерфейс, вопросы, динамическое ТЗ, проверки, подборка исполнителей и сравнение предложений.

## Порядок работы по каждой категории

1. **Исследование категории**
   - официальная техническая документация;
   - инструкции производителей и профильные руководства;
   - обязательные требования и ограничения;
   - реальные варианты состава работ;
   - типовые ошибки и риски;
   - что влияет на цену и сопоставимость предложений.

2. **Определение модели объёма работ**
   - что клиент может заказать целиком;
   - какие отдельные части или зоны можно выбрать;
   - какие смежные работы должны быть отдельными опциями;
   - что нельзя автоматически включать в объём без согласия клиента.

3. **Динамический сбор исходных данных**
   - пользователь описывает задачу свободным текстом и/или фото;
   - сервис извлекает уже известные параметры;
   - задаются только недостающие вопросы, которые реально влияют на поиск, расчёт или риски;
   - формулировки должны быть понятны неспециалисту.

4. **Спецификация категории**
   Для каждой категории создаётся отдельный файл `docs/products/<category>.md`, где фиксируются:
   - варианты задач;
   - обязательные входные параметры;
   - условные и динамические вопросы;
   - структура технического задания;
   - обязательные поля предложения исполнителя;
   - исключения из объёма работ;
   - критерии соответствия задаче;
   - факторы проверки исполнителя;
   - сигналы риска;
   - источники и ссылки на документацию;
   - контрольные сценарии для интерфейса и логики.

5. **Машинный offer-contract категории**
   В `assets/category-profiles/<category>.json` обязательно фиксируются:
   - `contractorResponseRequired` — минимальные поля ответа исполнителя;
   - `outreachContract` — единый набор требований, отправляемый всем кандидатам;
   - `comparisonSchema` — поля итогового сравнения, их тип, группа и важность;
   - `clarificationPolicy` — когда сервис обязан запросить недостающую информацию;
   - `normalization` — правила сопоставимости и обработки неизвестных данных.

   Для каждого поля `comparisonSchema` указываются минимум:
   - `id`;
   - `label`;
   - `type`;
   - `importance`: `critical`, `important` или `optional`;
   - `group`.

   Категория не считается готовой для автоматического сбора предложений, если у неё нет этого контракта.

6. **Техническое задание исполнителю**
   - сервис фиксирует задачу и ожидаемый результат клиента;
   - сервис не назначает техническое решение вместо специалиста, если это требует профессионального проектирования или оценки;
   - исполнитель должен предложить решение, материалы и состав работ;
   - смежные и дополнительные работы выводятся отдельными строками, а не незаметно расширяют заказ;
   - предложения разных исполнителей должны приводиться к сопоставимому виду;
   - все исполнители одной задачи получают одну версию исходного запроса;
   - альтернативное техническое решение сохраняется отдельно и не подменяет исходное ТЗ.

7. **Сбор и нормализация ответов**
   - исходный ответ исполнителя всегда хранится без изменения;
   - нормализованное предложение хранится отдельно;
   - `unknown` не считается отрицательным фактом;
   - критические пробелы автоматически формируют уточняющие вопросы;
   - ответ на уточнение обновляет нормализованное предложение, сохраняя историю;
   - поля, которые достоверно определяются только на замере, не должны блокировать предварительное сравнение, если это явно обозначено.

8. **Разделение внутреннего исследования и клиентского интерфейса**
   - технические источники, производители, ссылки на инструкции и исследовательские заметки хранятся во внутренней спецификации категории;
   - названия производителей и брендов не выводятся клиенту как объяснение логики сервиса, если сам заказ не относится к конкретному бренду;
   - в клиентском интерфейсе показываются только понятные вопросы, итоговое ТЗ и выводы, необходимые для выбора;
   - внутренние технические обоснования не публикуются в сообщении исполнителю;
   - внешние факты об исполнителе всегда показываются отдельно с указанием источника.

9. **Проверка перед публикацией категории**
   - сбор исходных данных корректно работает для типового и частичного заказа;
   - ТЗ меняется в зависимости от выбранного объёма;
   - смежные работы не смешиваются автоматически;
   - обязательные параметры для сравнения присутствуют;
   - `comparisonSchema` покрывает цену, состав, критические технические параметры, исключения и условия;
   - gap detection создаёт уточнения по отсутствующим критическим полям;
   - исходный ответ исполнителя доступен отдельно от нормализованного представления;
   - источники внешних сведений отображаются отдельно;
   - карточки кандидатов и сравнение используют только релевантные поля категории;
   - в публичном интерфейсе нет внутренней исследовательской документации и лишнего профессионального жаргона.

## Текущий эталон

Первая категория и эталон реализации: `docs/products/balcony-insulation.md`.

Эталон offer-contract: `assets/category-profiles/balcony-insulation.json`.

Архитектура общего конвейера: `docs/offer-pipeline-architecture.md`.

По всем следующим категориям — кондиционеры, двери, сантехника, электрика и т. д. — сначала выполняется такой же цикл исследования и создания спецификации категории, а уже затем категория добавляется в интерфейс «Сделает».
