# Product Category Standard

Обязательный стандарт для добавления каждой новой категории услуг в «Сделает».

## Главное правило

Новая категория не добавляется в продукт только на основании универсального AI-промпта или общего списка вопросов.

Сначала категория изучается отдельно, затем создаётся Product Spec, и только после этого реализуются UI, вопросы, динамическое ТЗ, проверки, shortlist и сравнение предложений.

## Порядок работы по каждой категории

1. **Исследование категории**
   - официальная техническая документация;
   - инструкции производителей и профильные руководства;
   - обязательные требования и ограничения;
   - реальные варианты состава работ;
   - типовые ошибки и риски;
   - что влияет на цену и сопоставимость предложений.

2. **Определение scope-модели**
   - что клиент может заказать целиком;
   - какие отдельные части/зоны можно выбрать;
   - какие смежные работы должны быть отдельными опциями;
   - что нельзя автоматически включать в объём без согласия клиента.

3. **Динамический intake**
   - пользователь описывает задачу свободным текстом и/или фото;
   - сервис извлекает уже известные параметры;
   - задаются только недостающие вопросы, которые реально влияют на поиск, расчёт или риски;
   - формулировки должны быть понятны неспециалисту.

4. **Product Spec категории**
   Для каждой категории создаётся отдельный файл `docs/products/<category>.md`, где фиксируются:
   - варианты задач;
   - обязательные входные параметры;
   - условные/динамические вопросы;
   - структура технического задания;
   - обязательные поля предложения исполнителя;
   - исключения из scope;
   - критерии соответствия задаче;
   - факторы проверки исполнителя;
   - сигналы риска;
   - источники и ссылки на документацию;
   - acceptance cases для UI и логики.

5. **Техническое задание исполнителю**
   - сервис фиксирует задачу и ожидаемый результат клиента;
   - сервис не назначает техническое решение вместо специалиста, если это требует профессионального проектирования/оценки;
   - исполнитель должен предложить решение, материалы и состав работ;
   - смежные/дополнительные работы выводятся отдельными строками, а не незаметно расширяют заказ;
   - предложения разных исполнителей должны приводиться к сопоставимому виду.

6. **Разделение внутреннего исследования и клиентского интерфейса**
   - технические источники, производители, ссылки на инструкции и исследовательские заметки хранятся во внутреннем Product Spec;
   - названия производителей и брендов не выводятся клиенту как объяснение логики сервиса, если сам заказ не относится к конкретному бренду;
   - в клиентском интерфейсе показываются только понятные вопросы, итоговое ТЗ и выводы, необходимые для выбора;
   - внутренние технические обоснования не публикуются в сообщении исполнителю;
   - внешние факты об исполнителе всегда показываются отдельно с указанием источника.

7. **Проверка перед публикацией категории**
   - intake корректно работает для типового и частичного заказа;
   - ТЗ меняется в зависимости от выбранного scope;
   - смежные работы не смешиваются автоматически;
   - обязательные параметры для сравнения присутствуют;
   - источники внешних сведений отображаются отдельно;
   - карточки кандидатов и сравнение используют только релевантные поля категории;
   - в публичном UI нет внутренней исследовательской документации и лишнего профессионального жаргона.

## Текущий эталон

Первая категория и эталон реализации: `docs/products/balcony-insulation.md`.

По всем следующим категориям (кондиционеры, двери, сантехника, электрика и т. д.) сначала выполняется такой же цикл исследования и создания Product Spec, а уже затем категория добавляется в интерфейс «Сделает».
