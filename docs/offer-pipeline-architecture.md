# Архитектура конвейера предложений исполнителей

Статус: production foundation

## Цель

После подтверждения ТЗ «Сделает» должен не просто показать найденных исполнителей, а провести задачу через единый конвейер:

`ТЗ → кандидаты → одинаковый запрос → ответы → нормализация → пробелы → уточнения → сравнение → вывод → выбор`.

Пользователь не обязан самостоятельно разбирать сметы и задавать технические уточнения. Экспертность и приведение предложений к сопоставимому виду находятся на стороне сервиса.

## 1. Source of truth

Для каждой категории `assets/category-profiles/<category>.json` является машинным контрактом этапа сбора и сравнения предложений.

Обязательные секции:

- `contractorResponseRequired` — минимальные поля ответа;
- `comparisonSchema` — что показываем в сравнении;
- `outreachContract` — что одинаково запрашиваем у всех исполнителей;
- `normalization` — правила сопоставимости;
- `clarificationPolicy` — когда сервис обязан задать уточняющий вопрос.

`docs/products/<category>.md` остаётся экспертной спецификацией для человека и источником требований к машинному контракту.

## 2. Сущности production pipeline

### Outreach

Один отправленный запрос одному исполнителю.

Минимальные поля:

- `outreach_id`;
- `task_id`;
- `candidate_id`;
- `request_version`;
- `request_text`;
- `channel`;
- `status`;
- `sent_at`;
- `delivered_at`;
- `last_reply_at`.

### Raw reply

Каждое исходное сообщение исполнителя сохраняется без изменения.

Минимальные поля:

- `reply_id`;
- `outreach_id`;
- `candidate_id`;
- `message_text`;
- `channel`;
- `received_at`;
- `raw_payload`.

Исходный ответ нельзя заменять нормализованной версией.

### Normalized offer

Текущее структурированное состояние предложения одного исполнителя по одной задаче.

Минимальные поля:

- `offer_id`;
- `task_id`;
- `candidate_id`;
- `outreach_id`;
- `total_price`;
- `work_price`;
- `materials_price`;
- `price_type`;
- `comparison_data_json`;
- `exclusions_json`;
- `extra_costs_json`;
- `completeness_score`;
- `comparable`;
- `normalization_version`;
- `updated_at`.

### Clarification

Уточнение создаётся, когда для сравнения отсутствует обязательное поле или есть противоречие.

Минимальные поля:

- `clarification_id`;
- `offer_id`;
- `field_id`;
- `question`;
- `status`;
- `sent_at`;
- `answered_at`;
- `answer_text`.

## 3. Правила отправки запроса

Все исполнители одной задачи получают один `request_version` и одинаковое исходное ТЗ.

Персонализироваться могут только:

- имя исполнителя;
- канал отправки;
- технические данные доставки.

Нельзя менять состав требований между исполнителями, иначе сравнение теряет смысл.

Исполнитель может предложить расширенный объём работ, но он сохраняется как отдельная альтернатива и не подменяет исходное ТЗ.

## 4. Нормализация

Система всегда хранит отдельно:

1. что буквально написал исполнитель;
2. что извлечено из ответа;
3. что подтверждено уточнением;
4. что осталось неизвестным.

Для каждого сравниваемого поля используется состояние:

- `confirmed` — явно подтверждено ответом;
- `claimed` — заявлено исполнителем, но не проверено внешне;
- `unknown` — данных нет;
- `not_included` — явно не входит;
- `requires_clarification` — без уточнения нельзя корректно сравнить;
- `requires_site_inspection` — достоверно определяется только после осмотра/замера.

Нельзя превращать `unknown` в отрицательный факт.

## 5. Gap detection

После каждого нового ответа система проходит `comparisonSchema` категории.

Уточнение обязательно, если:

- отсутствует поле с `importance = critical`;
- цена указана как «от»;
- неизвестно, входят ли материалы;
- отсутствующая работа меняет сопоставимость цены;
- ответ противоречит предыдущему ответу;
- дополнительная работа влияет на итоговую стоимость.

Необязательные поля не должны блокировать сравнение.

## 6. Comparison result

Итоговая страница должна показывать:

- сколько предложений получено;
- сколько полностью сопоставимы;
- сколько требуют уточнения;
- итоговую или сопоставимую цену;
- состав работ и материалов;
- исключения и возможные доплаты;
- сроки;
- гарантию;
- договор;
- необходимость и стоимость замера;
- факты проверки исполнителя отдельным слоем;
- исходный ответ исполнителя по запросу пользователя.

## 7. Вывод «Сделает»

Сервис не присваивает абстрактный процент надёжности и не гарантирует исполнителя.

Допустимые выводы:

- лучшее по совокупности условий;
- самое дешёвое сопоставимое предложение;
- наиболее полное предложение;
- хороший баланс цены и комплектации;
- требует уточнения;
- пока нельзя корректно сравнить.

Каждый вывод должен иметь объяснимые причины на основании полей предложения.

## 8. Первая production-категория

Эталон: `BALCONY_INSULATION`.

Для неё полный pipeline считается готовым только после end-to-end сценария:

1. пользователь подтверждает ТЗ;
2. сервис получает реальные кандидатуры;
3. одинаковый запрос фиксируется для нескольких исполнителей;
4. сохраняются реальные ответы;
5. ответы нормализуются по `comparisonSchema`;
6. система формирует уточнения по пробелам;
7. ответы на уточнения обновляют предложение;
8. итоговая страница строится из server-side данных, а не только из `localStorage`;
9. пользователь выбирает исполнителя;
10. дальнейший follow-up/review/recovery работает по уже существующей цепочке.

После успешного production E2E этот механизм масштабируется на остальные категории через их category profile.
